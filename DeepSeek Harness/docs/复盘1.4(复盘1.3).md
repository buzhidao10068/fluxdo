## 二、导出的复查发现及本轮处置

### 1. CI 在干净检出后缺少本地化生成文件——已修复

位置：`.github/workflows/quality.yaml`、`lib/l10n/app_localizations.dart`、`.gitignore`。

原流程为 `flutter pub get → flutter analyze → flutter test`。但本地化入口必须引用：

```text
lib/l10n/slang/strings.g.dart
lib/l10n/generated/app_localizations_compat.g.dart
```

这两组文件不入库；`flutter pub get` 不运行项目的自定义 slang 生成器。本地已有文件时测试能通过，干净检出时则会出现缺失文件和类型错误。前一轮已用最小副本复现 **6 条分析错误**。

本轮改为：

```text
flutter pub get
dart tool/gen_l10n.dart
flutter analyze --no-pub ...
flutter test --no-pub ...
```

在 analyze 之前执行生成器，之后的 analyze/test 使用 `--no-pub` 复用已解析依赖。本轮为既有门禁增加 Android Manifest 测试；保留此前的跨平台 scheme、ECH 和 Rust 回归检查，不把它们的存在当作本轮的平台验收。

全量 Flutter 测试维持原有非阻塞设置。本轮没有重新归因全量历史失败；“245 个失败”等数字是前序文档记录，不能作为本轮新实测结果。

### 2. Android 未显式关闭 Flutter 默认深链处理——已修复

位置：`android/app/src/main/AndroidManifest.xml` 的 `.MainActivity`。

应用已经使用 `app_links` 和 `DeepLinkService` 分发链接，Manifest 却没有按插件要求关闭 Flutter 默认深链处理。两套路由入口并存存在重复处理或路由冲突风险。

新增：

```xml
<meta-data
    android:name="flutter_deeplinking_enabled"
    android:value="false" />
```

依据：[app_links Android 设置文档](https://github.com/llfbandit/app_links/blob/main/doc/README_android.md)。

本轮先运行新增测试确认能发现问题：**修复前 4 条 Android Manifest 测试中 1 条失败、3 条通过**，失败点正是缺少该 metadata；补齐后随定向集全部通过。

测试同时验证 `singleTask`、`exported`、VIEW/BROWSABLE/DEFAULT、www/裸域、HTTP/HTTPS、三类路径和两个自定义 scheme。采用 XML 解析，而不是仅搜索文字，防止注释中的声明或错误层级让测试误通过。

### 3. Android App Links 服务端条件未满足——客户端声明保留，系统验收待完成

上一轮在本次会话中实时读取：

```text
https://www.nodeloc.com/.well-known/assetlinks.json → 404
```

Manifest 的 12 个网页链接 filter 已覆盖：

- 主域 `www.nodeloc.com` 与裸域 `nodeloc.com`；
- HTTP 与 HTTPS；
- `/t/`、`/u/`、`/session/email-login/`。

其中 6 个 HTTPS filter 保留 `autoVerify="true"`，为服务端关联就绪后使用。**不能通过删除 autoVerify 或仅补声明来替代站方验证。**

本轮修正了裸域 filter 的注释：每个 host 都需要自己的 `/.well-known/assetlinks.json` 直接返回有效关联，不能依赖裸域 301。Android 12+ 的未验证网页链接通常由浏览器打开，不应笼统承诺一定弹 chooser；用户手动批准域名和显式 Intent 是不同的测试条件。

没有修改站点、发布关联文件或联系站方。本机 `adb devices -l` 没有设备，因此真机自动唤起仍未验收。

## 六、Android 系统深链待办与验收方法

1. 确认最终 Android applicationId 和实际分发 APK 的签名证书 SHA-256。当前 applicationId 仍为 `com.github.lingyan000.fluxdo`；包名调整属于后续 P4，调整后必须同步服务端关联。
2. 由站方在 `www.nodeloc.com` 与 `nodeloc.com` 的 `/.well-known/assetlinks.json` 托管正确关联，relation 使用 `delegate_permission/common.handle_all_urls`，target 使用 `android_app`、实际包名与真实证书指纹。每个 URL 直接返回有效 JSON，不能用根域跳转替代文件。
3. 在安装对应签名 APK 的 Android 设备执行重新验证并查看结果：

   ```sh
   adb shell pm verify-app-links --re-verify com.github.lingyan000.fluxdo
   adb shell pm get-app-links com.github.lingyan000.fluxdo
   ```

4. 验证正常浏览器场景的点击唤起，覆盖冷启动、已启动、www/裸域与话题/用户路径。邮箱登录与真实授权回调需要真实有效凭证，完整登录链路留到 P2。
5. 本地诊断路由可以使用显式组件 Intent，但必须与系统自动域名接管分开记录：

   ```sh
   adb shell am start -W -a android.intent.action.VIEW -c android.intent.category.BROWSABLE -d "https://www.nodeloc.com/t/123" -n com.github.lingyan000.fluxdo/.MainActivity
   adb shell am start -W -a android.intent.action.VIEW -c android.intent.category.BROWSABLE -d "fluxdo://topic/123" -n com.github.lingyan000.fluxdo/.MainActivity
   ```

   `123` 只是路由样例，真实浏览验证需替换为存在的话题。显式 Intent 绕过系统域名选择，只能验证交给 App 后的处理，不能据此声称 App Links 验证成功。
