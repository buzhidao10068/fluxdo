## 二、确认问题与修复状态

### 1. 当前书签账号没有随认证变化重新绑定

**优先级：P1；状态：已修复。**

原 `currentUsernameProvider` 只读取本地用户名，没有订阅认证变化。全局刷新即使清空候选列表，后续 `ensureLoaded()` 或仓库变更通知仍可能使用旧账号重新加载；切换账号时也可能继续展示旧账号的本地书签。

修复：[user_content_providers.dart](../../lib/providers/user_content_providers.dart) 中的账号 provider 订阅认证状态及 Discourse 服务变化，并继续从本地会话读取用户名，避免为了确定本地缓存隔离键而等待远端资料。候选、列表和同步控制器依赖该账号重建。

验证：实际执行退出清理后再调用 `ensureLoaded()`、向旧账号仓库写入数据，以及 alice → bob 切换，确认候选和列表对应当前账号。

### 2. 连续认证广播被相等值过滤

**优先级：P1；状态：已修复。**

本轮实测发现，原 `StreamProvider<void>` 收到的连续事件值均为 `null`。当前 Riverpod 3 会过滤相等值，第二次认证变化可能无法通知依赖，导致首次切换正常、随后退出或再次切换失效。

修复：[core_providers.dart](../../lib/providers/core_providers.dart) 将认证广播映射为递增的整数版本，`authStateProvider` 改为 `StreamProvider<int>`；[main.dart](../../lib/main.dart) 和 [topic_detail_page.dart](../../lib/pages/topic_detail_page/topic_detail_page.dart) 同步监听类型。Discourse 服务原有的 `Stream<void>` 接口保持兼容。

验证：在同一个真实 provider 容器内连续发出 bob 登录与退出事件，确认第二次事件也重新读取账号、清空书签列表和候选。该测试直接覆盖了之前遗漏的连续广播问题。

### 3. 清空状态不足以阻止迟到的书签读取与同步响应

**优先级：P1；状态：已修复。**

原实现没有把异步任务绑定到启动时的会话。候选初始化、仓库读取、列表分页或网络对账在 reset 后完成，仍可能恢复旧状态；旧同步任务占用的 inflight 标记还可能阻止新账号同步。订阅清理若读取可变字段，也可能误取消后续创建的新订阅。

修复涉及：

- [bookmark_name_suggestions_provider.dart](../../lib/providers/bookmark_name_suggestions_provider.dart)：为初始化与仓库派生读取增加 generation 和生命周期检查；清空时释放账号与初始化任务引用；销毁时取消当次 build 捕获的订阅。
- [user_content_providers.dart](../../lib/providers/user_content_providers.dart)：列表 build、仓库刷新和分页在异步等待后确认 generation；重建时清空分页状态，并取消当次订阅。
- [bookmark_sync_controller.dart](../../lib/providers/bookmark_sync_controller.dart)：reset 释放旧同步、下拉刷新、节流与失败状态；旧任务的 finally 不再清除新任务标记。
- [bookmarks_reconciler.dart](../../lib/providers/bookmarks_reconciler.dart)：三种对账入口支持 `isCurrent` 检查，并使用 `cancelled` 终止原因；会话失效后到达的网络响应不再继续处理。

验证：使用真实 Hive DAO 和 repository，在 alice 的仓库读取及网络分页被延迟时切换 bob，再释放旧请求。旧读取不能覆盖 bob 的列表和候选，旧网络响应不能写入该测试中的旧账号仓库，也不能结束新同步状态。

### 4. 全局刷新与退出清理缺少完整生命周期管理

**优先级：P1；状态：已修复。**

原全局静态去抖时间会跨容器共享，并可能在两秒内跳过账号重绑；延迟刷新在退出或容器销毁后仍可能访问容器。退出流程未完整等待用户与 Summary 缓存清理，某项清理失败时也需要确保另一项继续完成。

修复：[app_state_refresher.dart](../../lib/providers/app_state_refresher.dart) 按 `ProviderContainer` 保存去抖时间和刷新 generation；账号重绑先于普通页面刷新去抖；延迟回调检查 generation 与独立 lifetime 状态。退出时使旧延迟刷新失效，同时启动并等待两项缓存清理，立即挂接错误处理，一项失败仍等待另一项完成后向调用方报告。

清理候选和同步 provider 时先判断其是否存在；未初始化的 provider 直接由账号失效触发后续加载，避免“提前创建后立即清理”使首次候选为空。

验证：两秒内 alice → bob 刷新仍重绑账号；容器销毁后待执行的延迟刷新不抛异常；退出在两项异步清理均结束前不会完成，其中一项失败时另一项仍完成清理。

### 5. 用户与 Summary 请求在清理或销毁后仍可能写回

**优先级：P1；状态：已修复。**

原异步加载与刷新缺少足够的生命周期检查。旧请求在 clearCache、provider 重建或容器销毁后返回，可能重新写入用户/统计缓存，或访问已失效的 ref。

修复：[core_providers.dart](../../lib/providers/core_providers.dart) 中的 `CurrentUserNotifier` 和 `UserSummaryNotifier` 在 build、dispose、clearCache 时更新 generation；网络与缓存等待后检查当前有效性；缓存写入改为可等待的 Future，并在两个关联键写入之间再次检查。Summary 主动刷新增加请求序号，丢弃已被更新刷新替代的响应。

验证：Summary 刷新在 dispose、clear、切换 bob 后返回，首次 Summary 加载中销毁容器，以及用户静默刷新中 clearCache，均不会在这些测试时序下恢复旧缓存或抛生命周期异常。

这项修复拦截的是失效后的异步继续执行；**不保证已经提交给平台的磁盘写入与退出之间具备严格事务性**，具体边界见第五节。

### 6. 损坏的底层统计配置类型没有安全回退

**优先级：P2；状态：已修复。**

原 provider 在 try 外调用 `getString('profile_stats_config')`。如果旧数据或手工备份将该键写成 int、bool 或列表，类型异常会先于 JSON 解析处理抛出，个人统计配置无法加载。

修复：[profile_stats_provider.dart](../../lib/providers/profile_stats_provider.dart) 先使用 `prefs.get()` 检查底层类型，仅解析字符串；损坏类型或无效 JSON 回退默认配置，并写回规范 JSON。原有 Connect → Summary 归一化规则继续有效。

验证：三类底层错误类型及无效 JSON 均回退默认配置，重新加载 SharedPreferences 后能读取修复后的字符串。

### 7. 备份逐项解析与写入可能留下部分导入

**优先级：P1；状态：已修复。**

原导入边检查边写入：前面的配置已改变后，后面的错误类型或 API Key 才暴露问题。文件解析只检查部分外层结构，也会把无效内容留到实际恢复时处理。

修复：[data_backup_service.dart](../../lib/services/data_management/data_backup_service.dart) 在任何写入前构建完整导入计划，检查 v1/v2、data、条目结构、声明类型与实际值、StringList、有限 double、API Key，以及统计配置必须为字符串。文件解析复用完整预检。旧生态及其他被排除字段先过滤，即使其历史值损坏也不妨碍普通配置恢复。

文件解析的异常提示不再依赖 `S.current` 和 UI navigator context，服务可独立读取备份。

验证：未知/缺失版本、错误外层结构、错误条目类型、混合类型列表、错误统计配置及 API Key 均在修改配置之前被拒绝；v1/v2 正常导入和旧生态过滤继续通过。

### 8. 平台写入失败没有恢复已修改项

**优先级：P1；状态：已修复。**

原导入未处理 SharedPreferences setter 返回 `false` 的情况，异常也不会恢复此前写入；平台甚至可能先改值再返回失败，失败的当前项同样需要恢复。

修复：[data_backup_service.dart](../../lib/services/data_management/data_backup_service.dart) 保存待修改配置和 API Key 的原值，记录每个尝试写入项；setter 返回 `false` 视为失败，失败后逆序恢复。恢复单项失败仍继续处理剩余项，最终通过 `BackupRollbackException` 保留原异常和恢复错误，避免误报成功。

验证：SharedPreferences 平台桩模拟“先写入再返回 false”和“先写入再抛错”，随后 reload 验证原有字符串/列表恢复、新增键移除。持续失败测试确认错误被报告且其他配置仍继续恢复。API Key 的 mock 导入、导出成功路径通过；系统安全存储故障回滚未单独注入验证。

## 五、验证边界与仍需保留的限制

- **网络与设备边界**：认证、用户和 Summary 请求使用假的远端 Discourse 服务；书签使用真实 Hive DAO/repository，存储位置为测试目录。SharedPreferences 平台失败由桩注入，API Key 使用 FlutterSecureStorage mock。这些测试覆盖实际 provider、刷新、导入导出代码，但不代表远端退出 API、系统安全存储或真机登录已验收。
- **存储一致性边界**：generation 检查不能撤销已经开始的平台 I/O。SharedPreferences 关联键不是数据库事务；备份恢复属于失败后的补偿，无法承诺断电、进程崩溃或底层持续不可用时完全回到原状态。本轮也没有给多个并发导入调用增加串行事务控制。
- **未执行检查**：未重跑全量 Flutter 测试、未构建 APK、未真机登录、未验证远端 GitHub Actions，也未重跑 Rust 测试。系统安全存储抛错及其回滚未专门注入测试。
- **迁移范围**：ECH/Rust 远端交付、验证码和登录适配、站点安全名单、头像配色、包名与分发品牌不由本轮结论代替验收。工作区原有相关修改继续保留。
