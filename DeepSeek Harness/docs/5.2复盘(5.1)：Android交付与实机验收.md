## Android 编译修复

实际定位表明，先前的全插件 namespace 报错由 PowerShell 参数拆分引起：未整体引用的 `-Pandroid.overridePathCheck=true` 被拆为 `-Pandroid` 与 `.overridePathCheck=true`，将 Gradle `android` 扩展覆盖为字符串。整体引用参数后无需 namespace 兜底。

按 CODEX.md 查询 pub.dev 后，将 `chat_bottom_container` 从 0.4.1 升级到当时最新稳定版 0.5.4，依赖解析通过。该升级不作为上述参数错误的根因修复。

`flutter_avif_android 3.1.0` 同时包含同名 Java/Kotlin 插件类。仓库 Gradle 配置排除该插件的 Java 源根，仅编译 Kotlin 实现，替换上游直接删除 pub-cache Java 文件的做法。统一 Java/Kotlin 17 和 quickjs 链接 liblog 的现有修复保留。

在 JDK 21、Gradle 8.14、AGP 8.11.1、Kotlin 2.2.20 下，执行：

```powershell
.\gradlew.bat :app:compileDebugKotlin '-Pandroid.overridePathCheck=true' '-Ptarget-platform=android-arm64' --console=plain
```

结果为 `BUILD SUCCESSFUL`，703 个任务，日志 `build/android_delivery_5_1/kotlin-avif.log`。这是原工作区的 Kotlin 编译证据，独立检出 APK 验证另行记录。

Android minSdk 调整为 28，与 cargo-ndk `--platform 28` 一致。Android Rust 构建增加 `--locked`。Flutter 3.47.4 / Dart 3.13.3、SDK 36、NDK 28.2.13676358、cargo-ndk 4.1.2 为本轮工具链。

首次完整构建返回成功后，继续检查发现 CargoKit 的 Windows 批处理吞掉了 `rhttp` 和 `super_native_extensions` 的 Rust 编译错误，生成的 APK 缺少 `librhttp.so` 和 `libsuper_native_extensions.so`。该旧包不能用于验收。新增必要库清单后，核验脚本确实以非零退出码拒绝该包。

错误原因是插件调用 `rustup run stable cargo` 时按默认宿主选择 MSVC，而本机实际安装的是 GNU/MinGW 工具链，因此报 `link.exe not found`。将本机 rustup 默认宿主调整为 `x86_64-pc-windows-gnu` 后，`rustup run stable rustc -vV` 确认使用 GNU 宿主，再次构建。仓库不修改 pub-cache；Windows 工具链说明已补到 [开发文档](../../docs/development.md)。有完整 MSVC 工具链的机器无需照搬 GNU 宿主设置。

随后一次构建因磁盘空间不足失败，日志为 `apk-complete.log`，不能认定完整 APK 已生成。按用户要求清理原工作区旧 Android 编译产物、Rust target、`.pnpm-store/`、干净检出中已拒绝的缺库 APK、失效核验 JSON 及无效临时文件，共释放约 7.1 GiB，D 盘可用空间由约 16.65 GiB 恢复至 23.71 GiB。清理路径与完成时间记录在 `cleanup.json`；源码、Git 元数据、已有 review 证据、干净检出和可复用编译缓存保留。

## CI、干净检出与 APK

Android Delivery 已替换多平台标签发布流程，分支 push / PR 先执行 Quality Gate，再通过项目包装入口构建 arm64 debug APK。保留静态分析、五组定向 Flutter 检查、Node、Rust 默认/ECH 和非阻塞全量 Flutter 检查；全量结果保存日志。Flatpak 构建入口归档。无自动 Release 或标签创建。

候选模式要求维护者签名 secrets 与预期证书摘要；Gradle 在 `requireReleaseSigning=true` 时拒绝缺失的签名配置。普通 release 仍可能回退到 debug 签名。Firebase 默认关闭。

APK 核验脚本检查应用标识、版本、min/target SDK、签名、全部原生库 ABI、必要库清单、Rust gitlink、ECH 指纹、可装载 ELF 内容及三处 CA 一致性，并输出 JSON。实际构建、核验、CI 链接和哈希以本节后续记录为准。

手动工作流需要存在于默认分支；在 `fifth` 的工作流尚未合并到 `NodeLoc` 时，push 是本轮验证入口，不能宣称手动候选构建已可用。
