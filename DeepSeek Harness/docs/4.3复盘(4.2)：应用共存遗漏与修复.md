## 一、导出的审阅结论（修复前）

4.2 中记录的四项本地修复与当时代码基本一致。重新执行其 19 个回归文件，127 项全部通过，退出码 0；对应静态分析为 0 error、0 warning、120 info，退出码 0；差异空白检查通过。以上是本次追加修复前的验证，不代表原生安装共存已通过。

仍有三项应用共存问题，以及一项普通 Linux 安装的条件性遗漏。部分配置继承自原版，不将其全部归因为 P4 新引入的回归。

### 1. P2：macOS 默认安装路径与原版冲突

`macos/Runner/Configs/AppInfo.xcconfig` 的 `PRODUCT_NAME` 仍为 `fluxdo`，`.github/workflows/build.yaml` 的 DMG 同时提供 `fluxdo.app` 与 `/Applications` 拖放入口。

原版已安装在 `/Applications/fluxdo.app` 时，按默认方式拖入 fork 会遇到同名应用替换。独立 bundle identifier 不会改变安装目标文件名。手动改名或安装到不同目录可以共存，但默认分发流程仍未隔离。

修复要求：使用独立 `.app` 文件名，同步 Xcode 产品引用、Scheme、测试宿主、DMG 和构建检查路径。

### 2. P2：iOS CA 描述文件沿用原版系统标识

`lib/services/network/doh_proxy/per_device_cert_service.dart` 中，证书和外层描述文件分别使用 `com.fluxdo.doh-proxy-ca.cert`、`com.fluxdo.doh-proxy-ca`，并沿用原版的两个固定 `PayloadUUID`。

两个应用在独立沙盒内生成不同 CA，却向系统安装同一身份的描述文件。Apple 将 `PayloadIdentifier` 用于判断新增或替换已有描述文件，因此两版安装可能互相替换系统描述文件及其根证书信任。应用内的 `per_device_cert_installed` 布尔值不会随系统替换而更新。

应用内部另有 CA 信任锚点处理，因此不能由此断言另一版的全部 HTTPS 会立即失效。

修复要求：fork 专属且稳定的描述文件标识与 UUID、可区分的显示名，以及旧安装标记的失效策略。不得自动删除归属不明的旧系统描述文件。

### 3. P2：Windows 卸载无条件删除共用 scheme 注册项

`windows/setup.iss` 对 `Software\Classes\fluxdo`、`Software\Classes\discourse` 使用 `uninsdeletekey`，卸载没有检查当前 handler 归属。

安装 fork 后，如果原版或其他客户端在同一注册表范围接管了 scheme，再卸载 fork，卸载器仍会删除整个注册项。4.2 已将 handler 状态列为待验收，但这里可从源码确认实现缺陷，应明确列为未修复项。

修复要求：移除共用键的无条件删除，仅当当前处理命令的可执行文件确为本次卸载的应用时清理。继续保留 `fluxdo` / `discourse`，不能通过随意更换授权回调 scheme 解决。

### 4. P2（条件性）：普通 Linux 安装的启动入口仍与原版同名

`linux/CMakeLists.txt` 的可执行文件名仍为 `fluxdo`，安装的桌面文件仍为 `fluxdo.desktop`，其 `Exec=fluxdo %u`、图标和窗口匹配名称也未独立。

若两版接入同一桌面应用目录与 PATH，可能覆盖桌面入口或启动错误版本。当前 Flatpak 具有独立应用 ID 和导出的桌面文件，不能把这项直接认定为当前 Flatpak 发布包冲突；修改普通 Linux 二进制名时仍须同步 Flatpak 内部 wrapper，避免启动断链。

修复要求：独立 Linux 二进制和桌面文件身份、匹配的图标及窗口标识，说明普通 Linux bundle 的安装边界。

### Windows：覆盖安装时的旧卸载日志

仅删除当前脚本的 `uninsdeletekey` 仍不足以保护覆盖升级。Inno Setup 默认向旧卸载日志追加操作，已安装版本记录的无条件删键动作可能在下一次卸载时继续执行，绕过新增的归属检查。

本轮在 `[Setup]` 设置 `UninstallLogMode=overwrite`。同 AppId、同安装目录且安装模式匹配时，以新日志替换旧日志，使上述旧删键动作不再被继承。当前安装包完整重装自身文件；此方案的明确代价是：只存在于旧版卸载日志、当前包不再包含的文件，可能在卸载后残留。Inno 官方也因丢失历史清理记录而不推荐常规使用 overwrite，此处用于解除已知错误删键动作，不能将其解释为无代价的通用升级方案。

新卸载逻辑保守比较完整处理命令，不按 exe 文件名或路径子串删除；其他安装目录、其他程序或无法识别的命令均保留。卸载不会自动恢复上一个 handler，也不改变 Windows 默认应用选择。不同安装目录、不同安装模式、原版 AppId 的旧卸载器不受此修复控制；旧安装器降级覆盖也可能重新引入旧行为。

### iOS：描述文件与完成标记的升级

描述文件身份应在后续版本保持稳定，不能每次安装生成新的 UUID：

| 字段 | 当前值 |
|---|---|
| 外层 PayloadIdentifier | `com.buzhidao10068.fluxdo.doh-proxy-ca` |
| 证书 PayloadIdentifier | `com.buzhidao10068.fluxdo.doh-proxy-ca.cert` |
| 外层 PayloadUUID | `2A51D8CE-AE54-4EF6-8ED0-E96A9C69507C` |
| 证书 PayloadUUID | `DB16E462-6C07-4C05-A0A6-151A8D405753` |
| 安装确认 key | `per_device_cert_installed_nodeloc_v1` |

旧 `per_device_cert_installed` 不再使新引导判定为完成。升级后用户需重新安装并信任 fork 描述文件；已有设备 CA 文件可继续使用，不会因本次身份调整自动重新生成。`reset()` 清除当前完成标记后再清理当前 CA 文件和内存状态。旧系统描述文件归属不明，不自动删除。

`isCertInstalled()` 仍只读取用户确认，原生下载成功也不会自动设置该标记；它不能证明描述文件当前存在或系统仍信任证书。用户从系统设置删除描述文件或修改信任后，需要重新运行引导。备份服务按 `per_device_cert_installed` 前缀排除设备状态，新 key 继续被排除，并已补充备份回归断言。

`com.fluxdo/profile_install` 是进程内的原生通道，Dart 与 Swift 保持匹配即可，不因系统描述文件共存而机械更名。

### Linux：普通 bundle 与 Flatpak 的边界

普通 Linux 输出仍是含 `lib`、`data` 的完整可移动 bundle，应放在专属目录，例如 `/opt/fluxdo-nodeloc`，再将独立二进制名称接入 PATH，并集成桌面文件和图标；也可把实际安装的桌面文件 Exec 改为二进制的绝对路径。不能让两版共用整个 bundle 安装目录。

Flatpak 继续使用独立应用 ID，manifest 的 `command: fluxdo`、桌面的 `Exec=fluxdo %u` 与沙盒内 `/app/bin/fluxdo` 保持匹配，由 wrapper 转调 `/app/fluxdo/fluxdo-nodeloc`。它们不是需要继续替换的遗漏。

发布与升级说明已同步至 [docs/release.md](../../docs/release.md)，Flatpak 启动关系同步至 [docs/flatpak.md](../../docs/flatpak.md)。4.2 开头增加本报告链接，并说明首轮回归通过不能代表所有平台已完成共存。
