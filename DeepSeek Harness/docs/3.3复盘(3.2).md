## 二、P1：完整网页登录的迟到收尾可以越过流程失效

### 2.1 原因与实际复现

主要位置：`lib/pages/webview_login_page.dart` 的 `_checkLoginStatus`、`_finalizeLoginBeforeExit`、`_syncRuntimeCookiesBeforeLoginReady` 和 `_finalizeLoginBootstrap`。

原流程在进入收尾前检查一次 `_flowGeneration`，但保存用户名、读取 CSRF、同步认证 Cookie、读取 HTML 和预加载之间仍有异步等待。`dispose` 只释放控制器，没有使本流程失效；仅在最后导航前检查 `mounted`，不能保护此前的认证操作。

可复现的交错顺序：

1. 完整网页登录已经读取到用户名和本次 WebView 的 `_t`，进入 CSRF 脚本读取并暂停。
2. 用户返回关闭页面，或者执行退出的关键动作：推进 `AuthSession`、清空内存 token、清理 Cookie。
3. 迟到的 CSRF 读取返回，旧流程继续调用 `AuthSession().advance()`，取得新的代次。
4. 后续流程使用全局当前代次，而不是保持对原登录流程的约束；即使 Cookie 同步已拒绝旧快照、jar 仍为空，旧逻辑也会回退此前读取的 WebView token。
5. `setToken` 和 bootstrap 的成功或兜底回调继续恢复内存认证、广播登录成功。

修复前探针分别复现了销毁后继续推进代次、写入认证 Cookie并广播，以及换代清理后 jar 保持为空但内存认证与成功广播仍恢复。证据见 `build/review_p2_recheck/probes.log`，探针源码为同目录的 `webview_review_probe_test.dart`。

探针重放的是退出的关键状态变化，没有运行完整 `logout` 网络请求和 UI 端到端流程。这里确认的是可控制异步时序下的会话隔离缺口，不表示每次正常退出都会出现。相关收尾结构在 HEAD 已存在；P2 对此文件原有的改动主要是按站点跳过 NodeLoc 的 fingerprint 等待，并非本项缺陷的全部来源。

### 2.2 本轮修复

相关代码：

- `lib/pages/webview_login_page.dart:76`：统一 `_flowIsCurrent` 检查。
- `lib/pages/webview_login_page.dart:115`：`PopScope<bool>` 在成功 pop 当时取消流程。
- `lib/pages/webview_login_page.dart:516`：主流程的异步边界检查及失败后重试恢复。
- `lib/pages/webview_login_page.dart:620`：固定登录代次，核对 Cookie 后才设置内存 token。
- `lib/pages/webview_login_page.dart:692`：runtime 同步传递固定代次与局部取消。
- `lib/pages/webview_login_page.dart:893`：bootstrap 的有效性检查和一次通知约束。

流程同时绑定页面生命周期、局部取消、会话代次和 Cookie 清理代次。成功收尾推进代次后只记录本次取得的 `_loginGeneration`，后续不得收编其他流程的新代次。单独执行 Cookie 清理、没有推进 `AuthSession` 时，也能通过清理代次让旧流程失效。

系统返回和标题返回通过 `PopScope<bool>` 在路由成功 pop 时立即取消，覆盖 widget 仍处于退出动画中的窗口；`dispose` 也执行相同取消。关闭单个页面不额外推进全局会话代次。

用户名、CSRF、初始 Cookie 灌入、原生 `_t` 读取、认证同步、诊断、runtime 同步和 HTML 读取等关键等待之后均复查。BoundarySync 接收同一个局部取消条件，并使用前次修复已具备的底层写入保护。fingerprint 等待与本地取消信号竞争，避免关闭后仍无意义等待。迟到的 JS 与 WebView 生命周期回调不能重新启动收尾。

只有 jar 中 `_t` 与本次 WebView token 完全一致，才设置内存 token。缺失或不一致时返回失败，不再回退旧 token；有效流程会恢复去重及加载状态，允许后续页面事件重试。

bootstrap 的通知回调和 `finally` 同时检查流程有效性及 `loginReadyNotified`。`Future.timeout` 不会取消底层 Future，因此有效登录在 8 秒超时后可以执行一次既有兜底通知，迟到的成功回调不能再次广播；关闭或换代后的流程不能执行兜底通知。

### 2.3 修复边界

局部取消用于阻止失效流程继续认证收尾，不提供事务回滚：此前已经完成的 Cookie 写入、用户名保存或 `setToken` 不会因为随后关闭页面而自动撤销。真正退出时仍由会话换代、清理 token 和清理 Cookie 完成状态清除。

本轮没有改造公共 `LoginReadyCoordinator` 或 `PreloadedDataService` 的全部异步工作。局部关闭时，已开始的 HTTP 预加载仍可能完成并更新其缓存；正式测试明确等待该迟到响应成功处理，再验证没有成功广播。会话换代后的请求由既有 SessionGuard 取消。不能据此宣称所有底层 Future 或预加载解析都已经物理取消。

## 三、P2：Cookie 冷读的旧结果覆盖新缓存

### 3.1 原因与触发条件

位置：`packages/enhanced_cookie_jar/lib/src/enhanced_persist_cookie_jar.dart:35`，`_readAll`。

原实现先检查 `_cache`，为空则等待 `_store.readAll()`，返回后直接执行 `_cache = loaded`。普通公开读取不受持久化写队列整体串行保护，因此存在如下顺序：

1. 新建 jar 的缓存为空，公开读取取得旧磁盘快照后暂停。
2. `deleteAll` 完成，发布空缓存并删除磁盘 Cookie。
3. 旧读取返回，将已清空的缓存替换成旧 `_t`。
4. 后续保存无关 Cookie 时，旧 `_t` 随整个缓存重新落盘。

保存新 Cookie 或另一次冷读先发布新缓存时，也可能被首个迟到读取覆盖。修复前使用真实临时 `FileCookieStore` 复现了清理后旧认证值重新落盘，见 `build/review_p2_recheck/cold_read_probe_test.dart` 和 `probes.log`。

**该问题要求普通读取发生于冷缓存。** 生产初始化迁移会预热 `readAll`，常规退出时通常已存在缓存，不能将该复现描述为“正常退出必然恢复 Cookie”。`reloadPersistedCookies` 本身位于串行队列中，也不是此项复现的来源。本项是既有包实现缺口，与 `3.2` 已新增的可取消写入检查不同。

### 3.2 本轮修复

读盘返回后使用已经发布的缓存，仅当缓存仍为空时才接受本次快照：

```dart
final cached = _cache;
if (cached != null) return cached;
final loaded = await _store.readAll();
// 读盘期间清理、写入或其他冷读可能已经发布了新缓存。
// 迟到的磁盘快照不得覆盖它，当前读取也应使用最新缓存。
return _cache ??= loaded;
```

当前实现仅在 jar 创建时缓存为 `null`；清理、写入及重载都会发布非空缓存。因此无需新增版本计数器，迟到读取自身也能返回当前缓存，而不是把已失效的旧快照交给调用方。
