## 三、密码登录与会话收口

### mini WebView 主入口

1. 打开当前站点同源的轻量页面并显示 hCaptcha，不预先要求 `cf_clearance`，也不加载完整 Discourse Ember bundle。
2. 验证码通过后，在同一个 WebView 内执行 `GET /session/csrf`。请求携带 `Accept: application/json` 和 `X-Requested-With: XMLHttpRequest`，要求返回非空字符串 `csrf`。
3. 用验证码 token 请求配置的验证码端点，随后 `POST /session.json`。200 HTML 验证码错误页不能算验证成功。
4. 需要 TOTP 时保留同一个控制器；等待输入期间忽略重复验证码回调。第二次请求不重复消费 hCaptcha token。取消、备用码及安全密钥沿用已有 UI 处理和网页登录兜底。
5. 登录响应必须为 HTTP 2xx，且不存在 `error` / `errors`，并包含 `id > 0`、非空 `username` 的 `user`。保留 Discourse 业务错误和 2FA 提示。
6. 成功响应后从本次 WebView 的原生 Cookie store 读取 HttpOnly `_t`。为容纳原生存储延迟，最多读取 10 次，间隔 200 毫秒，总间隔最多 1.8 秒。
7. 执行站点 bootstrap，再通过可信边界同步写入 jar。只有 jar 中 `_t` 与本次读取值一致，且会话代次仍有效，才向调用者返回成功。
8. 服务层再次检查请求代次及 jar 中 `_t`，再推进 `AuthSession`、保存登录信息并通过 `LoginReadyCoordinator` 通知。异步收尾期间也检查代次，防止已退出或切换会话后旧流程继续广播成功。

上述校验防止匿名 `_forum_session`、空 JSON、错误页和残留 jar token 单独触发登录成功。尚未以真实账号验证 NodeLoc 登录后的 Cookie 下发行为。

### 原生 Dio 入口

保留 `verifyHcaptchaToken` 和 `loginWithPassword`，移除“Linux.do CSRF 必然被 CF 拦截”的弃用说明。本次没有将 UI 主入口切换成原生 Dio 登录。

原生验证码路径优先使用站点配置，其次是通用候选路径；仅 404 继续回退，其他错误停止，200 HTML 也视为失败。登录响应与 mini WebView 共用严格解析；附带有效 `user` 的 `DioException` 仍不能绕过正常成功路径。原生请求也携带启动时的会话代次，防止用后来会话的新 token 完成旧请求。

## 四、Cloudflare、fingerprint 与授权策略

### 按真实挑战触发 CF 兜底

保留 `cf_challenge_service.dart` 本体。本次仅调整登录流程的调用条件：CSRF 状态为 403/429，且共享 challenge 判定识别到真实挑战信号时才尝试手动验证，最多重试一次。普通 200 HTML、403、429、500 都不能仅凭状态或 HTML 触发过盾。

验证完成后同步 CF 等非认证 Cookie，排除认证 Cookie，避免旧会话写回；随后重试原登录请求。此处不强制要求产生新的 `cf_clearance`。

测试中发现取消 CF 页面后登录结果丢失：CF 服务会在下一帧的 post-frame 回调退出透明拦截路由，登录对话框立即 `pop` 会误退出仍在栈顶的拦截路由。调用方现在等待 `WidgetsBinding.instance.endOfFrame`，确认 CF 清理完成后再处理登录结果。回归通过实际 CF UI 的取消路径覆盖此时序。

### 站点决定 fingerprint 需求

`requiresFingerprint` 默认关闭，NodeLoc 沿用默认值；Linux.do 显式开启。NodeLoc 不再等待旧站 fingerprint 插件或 `_rt`，但 `_t` 登录检测、Cookie 同步及会话代次保护仍保留。

### User API Key 最小权限

- 普通授权名：`NodeLoc Unofficial Client`。
- 扫码授权名：`NodeLoc Unofficial Client QR Login`。
- `scopes = 'one_time_password'` 保持不变；未取得 `write` 支持证据前不扩大权限。
- `keyWorthKeeping == false`，沿用 OTP 兑换后撤销 key 的策略。
- 未以真实浏览器授权或跨设备扫码验收以上链路。

## 五、线上只读证据

2026-11-08 对 `https://www.nodeloc.com/session/csrf` 进行了只读 GET 复测：

| 请求方式 | 结果 |
|---|---|
| 不携带 AJAX / JSON 请求头 | HTTP 200 HTML，含 NodeLoc 页面标题，未见挑战标记 |
| 携带应用实际使用的 `Accept: application/json` 与 `X-Requested-With: XMLHttpRequest` | HTTP 200，`application/json; charset=utf-8`，包含非空 `csrf` |

JSON 响应的 `csrf` 长度为 97；未记录或输出其值。服务端响应标识为 Cloudflare，但无 `cf-mitigated` 头。

此证据说明 CSRF 请求需要使用正确的内容协商头，不能将 200 HTML 直接归因于 CF。证据有时效性，也不等于已确认所有登录请求免于风控。本轮未使用真实账号凭据 POST 登录。
