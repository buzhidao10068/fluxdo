# 5.1 Android 交付与实机验收推进计划

整理日期：2026-11-10。

目标：按依赖顺序完成 NodeLoc Android 客户端的可复现构建、真实账号使用和独立应用验收，再决定是否进入 P5。

本文是后续执行计划。本文编写时仅新增本文件，没有修改代码、执行构建或测试，也没有提交、推送或发布；下列执行项均未因本文建立而完成。

## 一、目标范围与调整

按本次用户要求，后续以 **Android 为唯一交付平台**。iOS、macOS、Windows、Linux、Flatpak 和 Web 不再作为本阶段的开发、构建、验收或发布目标，可以放弃相应维护。

- 首个验收目标为 `arm64-v8a` Android 真机。
- `x86_64` 可用于模拟器辅助验证，不能替代真机结论；`armeabi-v7a` 等其他 Android ABI 只有在明确承诺分发时才加入构建与验收。
- Apple 编译、Swift XCTest、Safari 描述文件、macOS 钥匙串、桌面安装器及 Flatpak 等历史待办退出本阶段验收范围。
- Flutter 共用逻辑、Rust 代理、登录、上传、Android 原生通道和 Android WebView 仍在范围内，不能因放弃其他平台而跳过共用代码的 Android 验证。
- Windows 或 Linux 仍可作为 Android 的开发、CI 宿主；放弃 Windows/Linux 客户端不影响使用这些宿主运行 Dart、Rust 和 Android 构建。
- 当前只记录范围调整。平台目录、既有实现和历史文档保留；后续收缩构建、发布和公开支持说明时，不把平台源码批量删除作为前置任务。

本文接续 [4.5 原生停止与异步完成语义复盘](4.5复盘(4.4)：原生停止与异步完成语义修复.md)，调整的是后续交付范围，不把历史上未验证的平台改写为“已通过”。

**下一步先做 Android 交付与实机验收。P5 是可选增强，不是本阶段的下一项必做功能。**

## 三、执行顺序

按 **范围与快照 → Rust 交付 → Android 编译修复 → Android CI 与干净构建 → 真实账号使用 → Android 系统集成 → 候选版本确认** 推进。

每一步记录实际结果和证据，达到本步完成条件后再进入依赖它的下一步。可以提前准备测试设备与用例，但不能用后续计划代替前置步骤的通过记录。

### 第 1 步：确认 Android 范围与工作区交付清单

执行内容：

1. 记录主仓和全部子模块的当前提交、修改与未跟踪文件，区分既有修改、本次必需修改及生成产物。
2. 明确首批只验收和交付 `arm64-v8a`，列出实际设备型号、Android 版本及构建工具链。
3. 确认 P4 源码、回归测试、资源、文档和工作流需要进入的提交范围；对文档重命名核对链接。
4. 保留既有工作区内容；干净检出验证使用独立目录，不通过重置或清理当前工作区实现。

完成条件：有明确的 Android 交付清单、目标 ABI、设备和快照记录，不再把其他平台待办作为 Android 前置条件。

### 第 2 步：完成 Rust 子模块的可获取交付

执行内容：

1. 复核本地 `8a5db83e` 中的 NodeLoc ECH 域迁移，以及 `ffi.rs`、`proxy.rs` 的监听绑定、停止等待和状态修复。
2. 在匹配的宿主工具链上运行 Rust 默认特性和 ECH 特性测试，保存命令、退出码和结果。
3. 将所需修复形成子模块提交并推送到实际可获取的远端。当前 `.gitmodules` 指向上游仓库；若修复只能交付到自有 fork，应同步调整子模块地址。
4. 主仓更新 gitlink，确保记录的是包含完整修复的提交。
5. 从独立干净检出执行递归子模块初始化，确认能获取该提交，且两个 Rust 文件无需本地补丁。

完成条件：其他机器和 CI 能仅凭主仓记录获得完整 Rust 修复。本地存在提交、主仓普通提交成功或本机测试通过，都不能单独满足此条件。

依据：[4.5 子模块交付边界](4.5复盘(4.4)：原生停止与异步完成语义修复.md)。

### 第 3 步：解决 Android 依赖与原生编译阻塞

执行内容：

1. 复现并记录 `chat_bottom_container 0.4.1` 的 `Namespace not specified` 错误。
2. 选择可随仓库复现的修复：优先评估适配当前工具链的稳定版本；必要时使用明确来源的 fork 或仓库内补丁方案。
3. 如新增或升级依赖，按 `CODEX.md` 要求先查询 pub.dev 当前最新稳定版本，记录实际选型与兼容性验证，同步锁文件。
4. 修复不依赖手工改全局 pub-cache，不采用给所有插件随意分配同一 namespace 的兜底方式。
5. 继续处理实际出现的 Gradle、Kotlin、Java、NDK、插件或链接错误，直至 Android 原生编译通过。

当前配置参考：Flutter 3.47.4、Dart 3.13.3、Gradle 8.14、AGP 8.11.1、Kotlin 2.2.20。执行时记录实际 Java、Android SDK、NDK、Rust 和 cargo-ndk 版本，核对本地与 CI 的差异。

完成条件：Android 配置与 Kotlin 编译成功，修复在独立检出环境中有效，没有依赖当前机器的手工缓存修改。

依据：[4.1 Android 构建阻塞与后续验收](4.1开工：P4参数与文案对齐.md)。本步通过后仍需完成 APK 构建。

### 第 4 步：建立 Android CI，并从干净检出生成 APK

执行内容：

1. 收缩或拆分现有构建、发布流程，使 Android 检查和产物生成不依赖 iOS、macOS、Windows、Linux、Flatpak、AltStore 或其凭据、产物及汇总任务。
2. 提供分支或手动触发的 Android 构建入口，上传验证用 APK；验证构建不依赖打 `v*` 标签触发公开发布。放弃其他平台不能通过跳过 Dart/Rust 共用检查实现。
3. 从干净检出解析依赖、生成项目所需本地化与资源，运行当前 Quality Gate 的站点身份、生态清理、站点定制、登录、上传、数据隔离和代理生命周期定向检查。
4. Rust 默认/ECH 检查必须针对主仓 gitlink 记录的提交执行。
5. 使用项目构建包装入口准备原生产物并生成 Android APK，确认 `libdoh_proxy.so` 来自当前提交的源码、启用预期 ECH 特性且 ABI 正确。
6. 检查 APK 的 applicationId、版本、最低 Android 版本、签名及原生库；与原生构建使用的 Android API 目标一并核对，记录实际支持范围。

仓库现有构建入口示例，执行时在根目录使用项目 SDK：

```powershell
& '.fvm/flutter_sdk/bin/dart.bat' tool/flutterw.dart build apk --debug --target-platform android-arm64 --dart-define=cronetHttpNoPlay=true
& '.fvm/flutter_sdk/bin/dart.bat' tool/flutterw.dart build apk --release --target-platform android-arm64 --dart-define=cronetHttpNoPlay=true --split-debug-info=build/symbols
```

这两条命令仅在本文中记录，没有在编写本文时执行。`tool/flutterw.dart` 会调用项目预处理和 Android 原生准备；当前原生准备启用 `ech`，并将对应 ABI 的库放入 `android/app/src/main/jniLibs/`。最终应检查实际构建输出，不能仅凭此调用关系认定打包正确。

开发验证可先使用 debug 包。当前 Gradle 配置在签名不完整时允许 release 回退 debug 签名，因此 **release 构建成功不等于正式签名完成**；最终候选包必须核验实际签名证书。

全量 Flutter 测试目前是非阻塞项。执行时检查当前失败用例：Android 核心链路及本次引入的回归必须解决；确认为无关的历史失败应逐项记录依据，不能只引用历史失败数量或工作流总绿灯。

完成条件：干净检出构建通过、阻塞检查通过、APK 可获取且能安装到目标真机。保留主仓/Rust 提交号、工具链、CI 链接、构建日志、APK SHA-256 和实际签名证书摘要。

### 第 5 步：真实账号完成登录与日常使用验收

使用第 4 步记录的 APK，在 Android 真机上执行。模拟器和模拟 Cookie 结果作为补充。

| 范围 | 验收内容 | 通过标准 |
| --- | --- | --- |
| 未登录浏览 | 首页、分类、话题、搜索、图片与站内链接 | 正常加载 NodeLoc，无旧站无效入口或错误路由 |
| 密码登录 | 真实 hCaptcha、正确密码、错误密码、验证码过期、取消和网络失败 | 成功后获得当前会话 `_t`；失败、取消和匿名 `_forum_session` 不得被判为登录成功 |
| 会话恢复 | 杀进程重启、前后台切换、会话过期 | 有效会话正常恢复，过期会话正确处理 |
| 会话隔离 | 退出重登、账号切换、登录中退出或取消 | 旧异步结果不能恢复旧账号，缓存与用户状态一致 |
| 内容发布 | 普通回复、首帖、私信、草稿恢复 | 字数和权限按各自站点设置处理，成功后能重新读取内容 |
| 上传与播放 | 图片、音视频、允许的文件类型、取消和失败重试、用户等级限制 | 文件名/MIME 正确，服务端拒绝被正确展示，发布后媒体可打开或播放 |
| 上传边界 | 低于、等于、超过站点当前限额 | 使用动态设置；现有严格边界在大小大于或等于上限时先压缩或拒绝 |
| 保留的登录入口 | TOTP、备用码/安全密钥回退、OAuth、Passkey、浏览器授权及扫码 | 每个对用户开放的入口均有实测结果；浏览器回调、兑换、撤销和取消正确 |

附件上限历史记录为 15360 KiB，即 15 MiB；普通回复历史最小字数为 1、私信为 3，首帖单独读取设置。验收时以站点当时返回的设置为准，不把历史值重新硬编码。

扫码需要第二台设备。缺少对应设备或账号能力时，相关方式标为“未验收”；如决定不支持，应明确收缩入口和支持说明后重新验证，不能直接标为通过。

若遇到真实 Cloudflare 挑战，验证完成后的重试与取消；未遇到则如实记录，普通 HTML 或一般网络错误不能自动当作挑战。

完成条件：登录 → 浏览 → 回复 → 上传 → 重启恢复 → 退出重登的核心使用链路通过；公开保留的其他登录方式有验收结论。

依据：[3.1 Android 真机待验收](3.1开工：P2登录链路.md)、[3.3 会话隔离复盘](3.3复盘(3.2).md)和 [4.1 上传规则](4.1开工：P4参数与文案对齐.md)。

### 第 6 步：完成 Android 独立身份与系统集成验收

执行内容：

1. **安装与升级**：核对实际 APK 包名和签名；检查首次安装、同签名覆盖升级、数据保留、图标及图标切换。
2. **原版共存**：原版与 NodeLoc 版分别登录，检查 Cookie、凭据、草稿、设置、缓存和通知归属；覆盖两种安装顺序及卸载其中一版后的行为，另一版仍可正常使用。
3. **Android 原生交互**：验证文件选择、下载与保存、分享、录音/转码、权限拒绝与取消，以及相关 MethodChannel 调用。
4. **链接与授权回调**：验证站内/站外路由、冷启动和运行中接收链接、浏览器授权返回，以及两版共存时 `fluxdo` / `discourse` scheme 的实际接收者。回调进入错误应用时不能验收为通过。
5. **App Links**：若承诺 HTTPS 自动打开，需站方为实际包名和签名配置 `assetlinks.json` 并在真机验证。暂不具备条件时，明确该能力未启用，验证实际保留的浏览器和回调路径；不把应用内路由通过当作系统域名关联通过。
6. **网络与代理**：在设备上覆盖默认网络、DOH/ECH 开关、重启、网络切换、Dart 请求与 WebView。启停和异常恢复应有界，状态未知时不能假报停止或并行启动新代理，检查目标端口释放与恢复。
7. **Android 信任路径**：检查 APK 内置证书、应用 HTTP 适配器和 WebView 的实际信任行为。设备 CA 与轮转仅在 Android 实际使用该路径时验收；不套用 iOS 描述文件或 macOS 钥匙串要求。

指纹确认不代表已探测到系统信任，停止监听不代表已有连接全部终止。沿用 4.5 的行为边界，并在 Android 实际调用路径中验证。

完成条件：目标真机上的独立身份、原生交互、回调及网络集成通过；未承诺的可选能力有清晰说明，保留的用户入口不存在已知不可用路径。

### 第 7 步：冻结 Android 候选版本并决定后续

执行内容：

1. 将验收期间的必要修复及回归测试整理为可追溯提交，再次确认所有子模块提交可获取。
2. 完成 Android 专用构建与发布配置：使用维护者自己的签名，其他平台任务、凭据和发布渠道不再参与 Android 成败判定。
3. Firebase 保持可选；未启用时构建与运行正常，启用时使用本 fork 自有配置。
4. 从最终候选提交的干净检出运行阻塞检查并构建正式签名 APK，记录主仓与 Rust SHA、CI 链接、产物校验值、签名摘要及符号文件。
5. 对最终候选 APK 复验安装/升级、登录、回复、上传、回调和重启恢复；若候选版本包含新的功能修复，补跑受影响回归与设备场景。
6. 更新公开资料为 Android 支持范围，补充本版本 NodeLoc 真机截图、安装要求和已知限制，保留上游来源与许可说明。
7. 验收完成后再作发布决定。完成候选包不自动代表已公开发布，也不使用发版标签代替普通构建验证。

完成条件：存在可追溯、可复现、已签名并完成目标设备验收的 Android 候选包，且验证对象与最终提交、产物一致。
